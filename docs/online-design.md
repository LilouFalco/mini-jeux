Identity and entry

Selecting online first restores a persisted Supabase Auth session, or creates an authenticated anonymous user with signInAnonymously. The anonymous user has an auth.uid and the authenticated database role. The public anon/publishable key alone is not a player identity. Guest and verified-email accounts have the same game permissions. No authenticated JWT means no lobby data, joining, game reads, mutations, or Realtime subscription.

A guest chooses a display name or receives a random friendly one. Display names are not passwords, recovery codes, unique handles, or claims to another person's seat. Store a bounded plain-text name, reject controls and bidi overrides, and render with textContent. Names may repeat globally. Inside a room, display a stable seat number alongside duplicate names. Do not expose email, tokens, provider metadata, or auth.users records as a public profile. Optional profiles contain only user ID and display name, with own-write and narrow explicit read policies. Room membership snapshots the display name rather than requiring a global searchable profile directory.

Explain that clearing site data, signing out as a guest, or switching device loses guest access. An optional account uses email magic links through Supabase Auth. For a guest upgrade, link and verify the email while retaining the same user ID using the documented updateUser email flow, with manual linking enabled where required. Do not call a fresh sign-in and silently orphan the guest's active seat. Once verified, later sessions use signInWithOtp and an allowlisted callback. PKCE/verifier and installed-iOS-PWA callback behavior must be tested before promising device handoff.

If the email already belongs to another account, do not reassign membership using a client-supplied old user ID. Initial release refuses an in-game merge, explains the conflict, and offers switching accounts only after leaving the current room. An eventual merge requires proof of both sessions and a trusted transaction. No same-name account merge or name-based seat recovery is allowed. Recheck tokens server-side; a locally decoded user object is not sufficient authorization.

Rooms and directory

A player can create a room with a custom name or join using that name. All initial rooms are publicly listed and openly joinable while waiting and not full. Show this clearly before creation. The public directory returns only a room locator, game, display name, host display name, occupied seats, capacity, waiting/playing/finished status and expiry. Playing rooms can remain visible but cannot accept late entrants. No internal state, participant auth IDs, channel capabilities, access hashes, private settings, or player secrets appear in directory responses.

Store the display name separately from its server-normalized lookup name. Proposed bounds are 3 to 40 characters, trim, Unicode normalization, collapsed whitespace and case-insensitive matching. Mirror server normalization for previews but never trust the client result. Scope active-name uniqueness globally so joining by name alone is unambiguous. A transactional unique constraint reserves the normalized name until the room expires or is closed. Collisions return a bounded friendly error with an alternative, never overwrite another room. Old links carry an unguessable UUID and must not join a newly created room that reuses an old name.

A name or an unguessable UUID does not make a listed room private. The initial UI has no misleading private switch. A later private-room feature would remove the room from the directory, use an independently generated high-entropy join code, hash it server-side using a maintained password-hashing library, verify in a trusted endpoint with attempt throttling, and still require authentication and membership. Do not ship name-as-password.

Creating and joining lock the room row, enforce game capacity, active user membership, expiry and waiting status, and atomically allocate a seat. Repeated joins return the existing seat. A player cannot set host_uid, another player's user ID, capacity outside the game bounds, a ready state for others, or playing status directly. No spectators initially. Two-player games require exactly two ready authenticated members. Undercover preserves 3 to 10 players, Time's Up 4 to 12, and Petit bac 2 to 10. These limits match the inspected existing game rules.

Proposed abuse defaults, configurable after load testing, are at most two owned waiting rooms and three joined unfinished rooms per user, three creates per minute, twenty joins per minute, bounded list pages, and a short burst budget on actions. Enforce counters transactionally server-side, not via disabled buttons. Use Auth CAPTCHA/Turnstile and Auth rate limits to slow anonymous identity farming. A determined attacker can create multiple guest identities, so per-UID quotas alone are insufficient. An authenticated Edge gateway with an IP-aware managed limiter can be added if public abuse warrants it; do not invent an IP address from untrusted request input. No per-message telemetry or high-frequency polling.

Data boundaries

Use an unexposed app_private schema for authoritative rooms, memberships, public game projections, private player state, server-only game state and action receipts. No browser role gets table write privileges. Enable RLS on all app tables as defense in depth, explicitly revoke default grants, and expose only narrow reviewed RPCs. Database owners and trusted backend administrators can access state; the promise is isolation between players, including the room creator, not secrecy from the database operator.

rooms holds UUID, game, display and normalized name, owner user ID, capacity, lifecycle, options restricted to safe settings, monotonically increasing version, game instance ID, topic epoch and expiry. room_members holds room/user composite uniqueness, seat uniqueness, ready, team, joined order and server heartbeat lease. room_public_state is the member-readable shared projection, not a dump of the engine object. private_player_state holds room/user-keyed own data that can be disclosed to that user in the current phase. room_server_state holds unrevealed assignments, queues and reducer inputs that nobody can read directly. action_receipts has room, actor, action UUID, request digest, committed version and a sanitized acknowledgement. It is required for idempotency, not optional audit history. Do not persist raw secret action payloads or full request/response bodies in it.

The directory is a paginated authenticated list_rooms RPC that returns the explicit safe projection only. Prefer this to a view that accidentally inherits owner privileges or exposes join paths to private tables. If a view is used later, use security_invoker where applicable and verify underlying RLS behavior. No broad table SELECT grant to make a lobby work.

get_room_snapshot returns only authorized member metadata and public game state for a current membership. get_my_player_state derives the user solely from auth.uid and returns only that player's phase-appropriate disclosure. No caller-selectable target user parameter. Both are bounded, explicit projection builders. No select-star-to-JSON helper is permitted. Authenticated users cannot query another player's state, server state, raw actions, or auth records using REST, GraphQL, nested joins or RPC parameter substitution.

SECURITY DEFINER functions are a deliberate narrow privilege boundary for membership checks and authoritative transactions. Use a minimally privileged non-login owner where practical, set search_path to the empty string, fully qualify every object, avoid dynamic SQL, and revoke EXECUTE from PUBLIC, anon, authenticated and any direct/default grants before granting only the specific public entrypoints to authenticated. Verify auth.uid is non-null and membership/role/phase for every supplied room ID inside each function, because definer functions can bypass RLS. Helpers remain non-exposed and non-executable by browser roles. Auth IDs passed as claimed actors are ignored. Never accept arbitrary JSON state replacement.

Action and authority contract

Each mutation carries room UUID, game instance ID, expected version, a random action UUID, allowed action type and a bounded typed payload. The database locks the authoritative row, checks current membership, seat, role, turn, lifecycle, deadline and rules, and either commits one transition with the next version and its receipt or rejects without changing anything. Parameter ranges and text lengths are checked before expensive processing. Start, join, leave, ready, settings, round advance, resignation and scoring use the same authority model.

Receipt lookup precedes stale-version rejection after authorization, so retrying a committed action returns the original acknowledgement without replaying it. Same action UUID with a different digest fails. Two distinct simultaneous actions for the same expected version cannot both commit. A stale client must refetch before another action, not silently rebase a move. Receipt uniqueness and state transition occur in the same transaction. Secrets are not echoed in a generic receipt. Short-lived own-state reads obtain any private result separately.

Simple board games and hidden-state party games use reviewed SQL RPC reducers with transactional validation. Prefer explicit game-specific handlers over one all-powerful generic JSON patch endpoint. For chess, do not implement a second chess rules engine in SQL. An authenticated Edge action endpoint verifies the JWT using supported Auth verification, loads the canonical chess snapshot, runs the existing maintained chess.js dependency and matching draw-rule wrapper server-side, and calls a backend-only compare-and-swap commit RPC. That commit locks the room, rechecks membership, game instance, expected version and receipt, then commits atomically. No stale Edge calculation can overwrite a newer action.

The chess commit helper is not callable by browser authenticated/anon roles. Edge backend credentials live only in platform secrets, never in static code, GitHub, URL, browser storage or service-worker caches. An Edge endpoint must not accept a precomputed board/result from the browser or expose its snapshot-loading helper. The backend-only helper accepts only the trusted Edge result and verified actor; repeated Edge requests can return their prior receipt without another move. If that role/secret deployment path is unavailable, chess online waits rather than trusting a client-generated winner. Dashboard/CLI deployment permission is a separate prerequisite from the public project URL and key.

Realtime is a notification layer

Use private Supabase Broadcast/Presence channels, config.private true, and RLS on realtime.messages tied to auth.uid and current membership. Disable Allow public access in Realtime settings. Do not add ALTER TABLE ENABLE ROW LEVEL SECURITY to realtime.messages, which is already protected and may reject that command. Separate broadcast SELECT permission from presence INSERT permission. Browser members may publish minimal advisory presence but never authoritative game-change broadcasts. Database-triggered notifications contain only room/game instance and committed version, not whole rows or old/new full records.

Presence payloads contain only advisory seat availability and a coarse status. They are untrusted and never decide turn, score, identity, host ownership or elimination. Do not include tokens, words, ships, targets, current cards or typed answers. A malicious client can lie about presence; membership and server heartbeat leases remain authoritative. Disable debug dumping of presence and channel payloads. There is no guaranteed recovery of missed broadcasts.

Realtime authorization is cached for a connection, not rechecked on each message. Membership removal alone does not instantly revoke an already joined channel. On departures/kicks, rotate the room topic epoch and publish future notifications only on the new topic. Snapshot calls and topic discovery recheck current membership. Old channels receive nothing new; no private gameplay data is ever broadcast even on current channels. JWT refresh and reconnect reauthorize subscriptions, but do not depend on a departed client voluntarily refreshing. Verify this behavior with an already connected removed user.

Subscribe, fetch snapshot, and refetch if any received version exceeds the fetched one. Ignore duplicate/older events, resync on version gaps, and refetch after reconnect, visibility return and action acknowledgement. Poll only as a bounded degraded fallback while an online room is visible. Leave removes subscriptions/listeners and clears in-memory private state. A fresh game increments game instance ID so delayed actions and old notifications cannot contaminate the next game.

Game-specific behavior and tests

Morpion has a shared nine-cell board, seat marks, turn and computed win/draw. place accepts a legal empty cell for the current actor only. The server computes the winning line. Test occupied cells, off-turn clicks, a forged mark/winner, two simultaneous final moves, draw, retry and reload. No undo of an opponent's turn or local AI in online mode.

Puissance 4 has a shared 6 by 7 board. drop accepts a column, not an arbitrary row or replaced board. The server applies gravity, detects four in each direction and draw, and rejects a full column. Test all winning directions, full columns, forged coordinates, wrong actor, simultaneous drops and reconnect.

Naval keeps each full placement only in server state and the owner's projection. Validate the existing 10 by 10 board and fleet lengths 5, 4, 3, 3, 2, bounds, straight lines, no overlaps and a complete fleet before locking ready. Opponents receive readiness and fired-cell results only. fire accepts one untried coordinate on the actor's turn. The server calculates hit, sunk and victory from hidden placements, never from a defender acknowledgement. Ship identity or coordinates are disclosed only when intentionally allowed for a fully sunk ship. The local Naval.shoot helper returns the ship object even on a first hit, so its raw return value MUST NOT be serialized online. Test forged fleets, duplicate shots, incomplete setup, out-of-turn firing, fake victory, and that one hit does not reveal the rest of an unsunk ship. The room creator has exactly the same secret access as any other player.

Qui est-ce LoL shares the selected 24-champion roster, not both targets. Each player selects a valid target from the roster using an own-secret RPC; it is locked before play. The server privately stores it and verifies final guesses, preserving the current correct-guess win and wrong-guess loss rule. Eliminated portrait notes are local or owner-private and are not evidence for adjudication. Questions and answers are spoken externally in the initial version; there is no imaginary built-in voice/chat. Test target access by the opponent and host, invalid roster IDs, a target change after start, forged outcome and simultaneous guesses.

Chess shares canonical starting position, legal move history, side to move and result. FEN alone is insufficient for repetition history. Edge validates from/to/promotion with chess.js, preserves castling and en passant, and computes checkmate/stalemate and the same existing draw rules. Threefold and 50-move claims require a valid request, including intended-move claims; fivefold and 75 moves are automatic with checkmate priority. Preserve the current documented limited insufficient-material detection rather than promising exhaustive dead-position analysis. Test promotion, castling through check, en passant, malformed SAN/history, illegal king exposure, wrong color, forged FEN, resign, claim abuse, simultaneous requests and rejoin with repetition history. No local undo or AI worker can mutate an online board.

Undercover has 3 to 10 members, with the existing optional Mister White from five members and existing role counts. The server draws the pair and assignments using secure randomness. A player initially sees only their own word, or the intentional Mister White notice, not their explicit civil/undercover role, pair, other words or full assignment. The creator is not a dealer with full-state access. Public state has phase, speaking order, alive members, readiness, revealed eliminations and scores only. Server-held role data computes elimination and victory. Each alive member gets one private ballot; reveal the aggregate only when voting closes, reject self/invalid/dead ballots per the documented variant, and resolve ties with a new ballot among tied candidates. Use all-ready progression and bounded server voting deadlines so the creator cannot fabricate votes. Mister White's eliminated-player guess is checked privately server-side. Elimination and end-of-game disclosure intentionally reveal the same facts as the current rules, without revealing living assignments early. Test all private projections from every seat, dead voting, ballot overwrite policy, tied votes, White guess access, repeat distribution requests and host inspection. Static offline word-pair lists remain in the application; someone can infer likely counterpart words from the public vocabulary. This design protects assignments in transit, not cheating by inference, collusion or reading the offline dictionary.

Time's Up has 4 to 12 members, two server-assigned teams and the existing three rounds. The selected pool and queue order stay server-side; only the active describer receives the current card. Other members receive phase, describer, team, scores, counts and server deadline. The same selected cards recur across rounds as intended, and spoken/found cards become shared knowledge intentionally. This is not a promise that a previously seen card can become secret again. Future queue order and the current card are still not sent to guessers or the host. Only the describer can mark found/pass before the server deadline; scoring and queue rotation commit atomically. Spoken correctness is social, not an automated speech judge. The server stores turn_end_at and returns server time for display offset. Reloading or changing device time cannot extend a turn. Expiry is settled idempotently on the next snapshot/action, optionally with a scheduled cleanup worker, so an always-on per-second job is unnecessary. A disconnected describer's clock continues. Questions, description and guessing need an external call; mime needs external video. No integrated voice/video is in scope. Test expiry races, last-card handling, non-describer card fetches/actions, fake client time, pause abuse and reconnection across a round boundary.

Petit bac has 2 to 10 members with shared categories, server-picked letter and deadline. Preserve the existing points 0, 5 and 10, normalized duplicates and letter-cycle behavior. The initial online variant adds private per-player text answers so remote players do not need a shared sheet. Each own answer is bounded, stored privately during the round, locked at STOP/deadline, and disclosed to room members only in review. Do not store drafts in public state or broadcast each keystroke. A server transition freezes all submissions together, rejecting late edits. Automatic checks cover empty answers, initial letters and duplicates, not semantic truth for every category. Review uses explicit per-answer player validation, a majority of the other players, with ties disputed and worth zero until resolved; with two players the other player approves. Totals are computed server-side from accepted marks, never a client total or arbitrary host score. This social review is a variant that must be explained before enabling online play. Test hidden submissions, direct access by host, accent/case normalization, duplicate points, last-moment edits, STOP races and forged totals. Keep the existing paper-based offline mode untouched.

Connectivity and ownership

A room creator can change allowed waiting-room settings and request start when all players are ready; it never controls authoritative game state or others' secrets. Server heartbeat leases, not Presence, govern host migration. Proposed initial lease is a heartbeat every 20 seconds and a 90-second grace period. A member-triggered transactional reconciliation can transfer organizer rights to the earliest connected eligible member after the lease expires, requiring at least one fresh heartbeat. No arbitrary client nomination.

Two-player active games reserve the missing seat during the grace period. The remaining player can then request an abandonment result computed server-side; reconnect before settlement restores play. Party games reserve the seat and keep secret assignments, with visible consent-based continuation or abandonment rather than silently replacing a player. Time's Up deadlines continue. A host departure alone does not end a game. Empty waiting rooms expire after a proposed 30 minutes without activity; finished and abandoned state has a proposed 24-hour retention. These are application defaults, not claims about platform limits. Cleanup must protect currently leased rooms and avoid deleting linked accounts. Supabase anonymous-user cleanup is a separate deliberate maintenance task, not something assumed automatic.

On network loss, disable online submissions and show reconnecting. Never continue a separate local branch as though it were the shared match, and never silently switch to AI. Keep only a pending action ID/digest and minimum retry metadata in memory; do not queue private actions to background sync or localStorage. An unknown outcome is resolved with its receipt/snapshot after reconnect. Existing offline games remain reachable via an explicit leave/back choice without overwriting their separate saved game.

Frontend and cache boundaries

Load a pinned official supabase-js v2 browser bundle only when online is selected. Prefer a locally vendored bundle and license/provenance so a CDN outage does not affect existing local screens; choose the actual version from current release documentation during implementation. This planning task installs nothing. Small online adapter modules connect game-specific controls to typed RPCs; existing offline engines remain separate, not a global monkey patch of localStorage or transport.

Only public project URL and publishable/anon key appear in shipped configuration, generated from public deployment environment values. Those values are intentionally visible and rely on RLS and function grants. Never ship service_role, database password, signing secrets, Edge credentials or mail credentials. Lock SDK imports and avoid remote dynamic code.

The existing sw.js handles same-origin root GETs and precaches a static FILES list; it does not need to intercept Supabase origins. Future changes must retain an explicit static asset allowlist, version bumps, and same-origin scoping, and must never cache API/Auth/function responses, authorization-bearing requests, secret projections, magic-link callback URLs, query tokens or private HTML. Auth callback paths/queries bypass SW cache matching before any ignoreSearch navigation fallback, and are immediately removed from browser history after consumption. Dynamic responses use no-store where controlled and no sensitive values in URL query strings.

Auth persistence belongs only to the SDK's designated session storage, not service-worker Cache Storage or a duplicated application save. Treat browser storage as accessible to same-origin JavaScript, not as a secure vault. Same-origin portfolio and other Pages apps share this origin's trust boundary; an XSS elsewhere can compromise this session. Use text-only rendering for all user content, avoid unsafe HTML, and audit third-party scripts. A dedicated origin would improve isolation later without blocking the prototype. If localStorage is unavailable, fail online gracefully or clearly use an ephemeral session; do not break solo saves.

Do not persist online ships, assignments, active cards or other people's answers in application localStorage, IndexedDB, analytics, error trackers, screenshots, console logs or action logs. Own secrets are held only in memory while that room is open and cleared on leave/signout. Player devices can still inspect their own legitimately disclosed data. Capture only error codes and bounded nonsecret diagnostic IDs. Server and Edge error paths must redact raw payloads and SQL detail that could include answers. Offline static word lists are vocabulary, not live assignments.
